# IncidentPilot

**AI-assisted incident investigation with evidence you can check and a human in control.**

When a service breaks, IncidentPilot reads the logs and metrics, finds the likely root cause, **cites the exact log lines behind its answer**, recommends a fix from a fixed pre-approved list, and verifies whether the fix actually worked. Nothing runs until a person approves it.

> Built for the Nebius x NVIDIA Global AI Hackathon 2026. The diagnosis is generated by an **NVIDIA Nemotron** model served through **Nebius Token Factory**.

**Authors:** Abhay (AI investigation engine and backend API) and Purnima (dashboard).

## Why it exists

During an outage, engineers dig through thousands of log lines to find the cause. A plain chatbot can sound convincing while being wrong. IncidentPilot is designed so you don't have to trust the AI blindly:

- **Evidence-backed:** every claim points to a real log or metric ID, and IDs that don't exist are rejected.
- **Honest about uncertainty:** it reports confidence, alternatives and limitations, and caps confidence when no deterministic rule agrees.
- **Safe by design:** the model never chooses or runs commands. Fixes come from an allowlist and need explicit human approval.
- **Verified recovery:** after a fix, a health check runs. A failed check is never reported as success.

## How it works

```
Dashboard (Next.js)  ->  API (FastAPI)  ->  Agent (LangGraph)  ->  Nemotron on Nebius
                                  ^
                          log_loader.py  (raw logs -> bounded evidence)
```

1. **Collect evidence.** Each log or metric gets a stable ID. Emails, tokens and passwords are redacted, and the evidence window is capped.
2. **Deterministic checks.** Plain regex rules (no AI) detect known signatures: database pool timeouts, a blocked event loop, rejected API tokens. If nothing matches, no signal is invented.
3. **LLM synthesis.** The model gets the evidence inside `<untrusted_logs>` tags with the instruction never to follow text found there, and must return JSON matching a schema.
4. **Validation.** The answer is rejected if it is not valid JSON, fails the schema, or cites an evidence ID that doesn't exist. There is one retry with feedback, then the investigation is marked `failed`.
5. **Recommendations.** Actions come only from the allowlist (`ACTION_CATALOG` in `agent.py`) and only when a rule justifies them.
6. **Approval and recovery.** A person approves, the simulated fix runs, and a health check decides whether the incident is resolved.

Incident status lifecycle: `open` -> `investigating` -> `action_pending` -> `monitoring` -> `resolved`.

## Run it locally

Requires Python 3.10+ and Node.js 18.17+.

### 1. Backend

```bash
python -m venv .venv
source .venv/bin/activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Create a `.env` file in the project root (never commit it):

```
ENVIRONMENT=prod
NEBIUS_API_KEY=your_key_here
FRONTEND_ORIGIN=http://localhost:3000
```

Create the key in Nebius Token Factory under **API keys**. Then list the model IDs available to you and set the Nemotron ID you want in `model_name` inside `config.py`:

```bash
python - <<'PY'
from config import settings
from openai import OpenAI
c = OpenAI(base_url=settings.openai_base_url, api_key=settings.api_key)
print([m.id for m in c.models.list().data if "nemotron" in m.id.lower()])
PY
```

Start the server:

```bash
uvicorn main:app --reload          # http://localhost:8000  (interactive docs at /docs)
```

**No key?** Set `ENVIRONMENT=local`, run `ollama pull llama3`, and the same code uses a local model. Smaller local models fail validation more often, so occasional `failed` results are expected.

### 2. Dashboard

```bash
cd frontend
npm install
cp .env.example .env.local         # contains NEXT_PUBLIC_API_URL=http://localhost:8000
npm run dev                        # http://localhost:3000
```

The header shows **Connected to API** when it is using the backend. With no `.env.local`, the dashboard runs on built-in demo data instead. Restart `npm run dev` after changing `.env.local`.

### 3. Investigate your own log file

```bash
python log_loader.py logs.txt                  # preview the evidence (no model call)
python run_on_logs.py logs.txt                 # run the full investigation in the terminal
LOG_FILE=logs.txt uvicorn main:app --reload    # adds incident INC-3001 to the dashboard
```

The loader expects loguru-style lines (`2026-10-28 09:33:32.096 | INFO | module:func:1 - message`). It removes request payloads and numeric user IDs before anything reaches the model.

## Deployment

The project is deployed as two services.

**Backend on Render**

| Setting | Value |
|---|---|
| Build command | `pip install -r requirements.txt` |
| Start command | `uvicorn main:app --host 0.0.0.0 --port $PORT` |
| `ENVIRONMENT` | `prod` |
| `NEBIUS_API_KEY` | set in Render's environment settings, never in the repo |
| `FRONTEND_ORIGIN` | the dashboard's URL, with `https://` and no trailing slash |

Run a single process (no `--workers`), because investigations are stored in memory.

**Dashboard on Vercel**

| Setting | Value |
|---|---|
| `NEXT_PUBLIC_API_URL` | the backend's URL, with no trailing slash |

Redeploy the dashboard after changing this value, because Next.js reads it at build time. Deployment Protection must be off for the public link to open without a Vercel login.

## API

| Method and path | Purpose |
|---|---|
| `GET /api/incidents` | List incidents |
| `GET /api/incidents/{id}` | Incident plus `latest_investigation_id`, `audit_events`, `metrics`, `recovery_note` |
| `GET /api/incidents/{id}/logs` | Logs for the incident |
| `POST /api/incidents/{id}/investigate` | Start an investigation (returns `202`). A repeat call while one is running returns the existing investigation. |
| `GET /api/investigations/{id}` | Status, `stage` (0 to 4 completed stages), report or error |
| `POST /api/incidents/{id}/remediations/{action_id}/approve` | Body `{"approver": "name"}`. Accepts only an allowlisted action recommended for that incident. |
| `POST /api/incidents/{id}/verify-recovery` | Re-run the recovery health check |
| `POST /api/demo/reset` | Restore the seeded state |
| `GET /health` | Liveness check |

Investigation statuses: `queued`, `running`, `completed`, `failed`.

Errors look like `{"error": {"code": "...", "message": "..."}, "code": "...", "message": "..."}`.

Example flow:

```bash
curl -X POST https://incidentpilot-56op.onrender.com/api/incidents/INC-2041/investigate
curl https://incidentpilot-56op.onrender.com/api/investigations/<investigation_id>
curl -X POST https://incidentpilot-56op.onrender.com/api/incidents/INC-2041/remediations/sim-reset-pool/approve \
  -H "Content-Type: application/json" -d '{"approver":"your-name"}'
```

Example report (inside `report` of a completed investigation):

```json
{
  "summary": "Database connection pool exhaustion is causing API timeouts.",
  "root_cause": {
    "hypothesis": "The pool reached its 20-connection limit and requests timed out waiting.",
    "confidence": 0.9,
    "evidence_ids": ["log-103", "metric-17"]
  },
  "affected_services": ["api-service", "postgres"],
  "alternatives": ["Slow query holding connections", "Connection leak"],
  "recommendations": [
    {"action_id": "sim-reset-pool", "title": "Reset simulated connection pool",
     "risk": "low", "requires_approval": true, "description": "..."}
  ],
  "limitations": ["Based on a seeded telemetry window."],
  "similar_incidents": []
}
```

The model is mocked, so tests need no key or network. They cover the happy path, empty or unrelated logs, prompt injection, secret redaction, malformed output, invented evidence IDs, provider failure, duplicate triggers, approval rules, a failed recovery check, and the log loader.

## Safety and security

- Logs are treated as untrusted data (prompt-injection defence).
- Secrets, emails and user IDs are removed before anything reaches the model.
- Model output is validated, and unvalidated text is never shown as a result.
- The model cannot choose actions, URLs, SQL or shell commands.
- Only allowlisted actions can run, and only after an explicit approval that is recorded in the audit trail.
- CORS is limited to `FRONTEND_ORIGIN`. Keep `.env` out of Git, and rotate any key that is ever committed.
- Raw log files can contain personal data. Don't commit them.

## Limitations

- **Data is in memory.** State is lost on restart or when the free Render instance sleeps, and the API must run as a single process.
- **Logs are loaded at startup,** either from the seeded incident or from `LOG_FILE`. There is no live log ingestion or connection to a log platform yet.
- **The demo fix is simulated.** There is one allowlisted action (`sim-reset-pool`), and the chart numbers for the seeded incident are demo values.
- **Detection rules are narrow.** They cover three signal types. Signals with no allowlisted action produce a diagnosis but no recommendation, by design.
- **Historical incident retrieval** (`similar_incidents`) is not implemented yet.
- Smaller local models are less reliable than the hosted model.

## Roadmap

- Ingest logs through an API or connector instead of at startup
- Store incidents, investigations and audit events in PostgreSQL
- More detection rules and more allowlisted, reviewed actions
- Retrieve similar past incidents as labelled historical evidence
- A labelled evaluation set with published accuracy and latency
